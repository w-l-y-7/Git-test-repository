# git-ignore：挑出不用提交的文件，写进 .gitignore

## 这个技能做什么

每次提交前，总有些"不用提交"的文件混进来（跑脚本生成的 csv/图、node_modules 那种大目录、IDE 的配置、带着密钥的 .env……）。这个技能帮你把它们认出来、拦在仓库外：

1. **全面扫一遍**：找没被跟踪的"垃圾" + 已提交进仓库的"垃圾"
2. **分门别类列清单**，一项项给你看
3. **你确认后**才把规则写进 `.gitignore`（新文件拦住）
4. **取消跟踪**你同意的已提交旧垃圾（文件留在硬盘，不再被 git 管）
5. 收尾时自查一遍，告诉你这次改了什么

**核心规矩：先看清单再动手。** 除非你明确点头，否则技能一步都不改文件。

## 执行步骤

### 第一步：收集情报（只跑命令，不翻文件内容，省时省 token）

两条 git 命令把全场扫出来，路径统一用 `-c core.quotepath=false`（中文文件名不乱码）：

```powershell
# 1) 没被跟踪、且现在也没被忽略的文件（= 新冒出来的、下次提交会带上的）
git -c core.quotepath=false ls-files --others --exclude-standard

# 2) 已被跟踪的文件全名单（= 已提交进仓库的，拿来认"漏网的垃圾"）
git -c core.quotepath=false ls-files
```

同时读一下现有的 `.gitignore`（用 Read 工具，UTF-8），记住已有哪些规则，别重复加。

> 注：`ls-files --others` 会自动尊重各级 `.gitignore`（包括子项目自己的），所以**凡是没出现在第 1) 条结果里的，就是已经被规则挡住的**，不用管。真需要管的只有两个地方：新冒出来的（第 1 条）、已提交但长得像垃圾的（第 2 条里挑）。

### 第二步：给文件归类

拿上面的名单，对照下面的"垃圾特征表"认人。**看到什么就归什么，宁可归不齐也别乱归。**

| 类别 | 特征（见到这些基本就是垃圾） | 例子 |
|---|---|---|
| **B 依赖/缓存目录** | 目录本身叫这些名：`node_modules`、`.venv`、`venv`、`__pycache__`、`.pytest_cache`、`.mypy_cache`、`dist`、`build`、`.next`；或文件是 `*.pyc` | 装依赖装出来的、跑测试缓存下来的，删了能重装 |
| **C IDE/系统文件** | `.vscode`、`.idea`、`.DS_Store`、`Thumbs.db`、`desktop.ini`、`*.swp` | 每台电脑都不一样，提交了别人也用不上 |
| **D 隐私/密钥** | 文件名叫 `.env*`、`*.pem`、`*.key`、`*.p12`、`*.db`、`*.sqlite*` | 里面是密码/密钥/账本数据，提交 = 泄露 |
| **A 脚本跑出来的产物** | 结尾是数据/图片/日志/中间文件：`*.csv`、`*.png`、`*.jpg`、`*.log`、`*.aux`、`*.out`、`*_report.csv` 之类，且名字像"跑一次脚本生成的" | 有代码在的话，重新跑一遍就能再生成 |

**三条红线：**

- **源代码、脚本本身（`*.py`、`*.js`、`.vue` 等）、说明文档、项目配置文件，一律不归为垃圾。** 它们是要提交的。技能的作用是拦"垃圾"，不是拦"你的劳动成果"。
- **拿不准的文件单独挑出来问用户**，绝不擅自归类、擅自加规则。
- 一条规则只写**具体那条文件/目录的路径**，别图省事写一刀切的 `*.csv`/`*.png`（万一下次想提交一张真图就误伤了）。

### 第三步：列清单，等用户点头（本技能最关键的一步）

把结果整理成**两份清单**给用户看，问清楚再动手：

**清单一「建议加进 .gitignore 的新文件」**（来自第 1) 条未跟踪名单，按类别 B/C/D/A 排好，每个文件前面标上类别；若是源代码，就标「建议提交」，不放进忽略清单）
例如：
```
[A 脚本产物]     LangChainRAG/langchain_rag_stress_report.csv
[A 脚本产物]     china_pop_2016_2026_2036.csv / china_pop_pyramid_*.png
[建议提交-别忽略] chart_pop.py / fetch_pop.py
```

**清单二「建议取消跟踪的已提交垃圾」**（来自第 2) 条跟踪名单里长得像垃圾的）
例如：
```
test.tex 之类之前手滑提交进去的，建议 git rm --cached
```

用 AskUserQuestion 或直接对话让用户确认，**两类分开问**：
- 清单一：全加 / 部分加（点名）/ 跳过
- 清单二：全取消跟踪 / 部分 / 跳过
- 顺手明确告诉用户哪些是"建议提交的代码"，别当成垃圾忽略掉

用户说"都不要"或啥都不剩 → 告诉用户「仓库挺干净，不用改」，收工。

### 第四步：把规则写进 .gitignore（只写用户确认过的）

新增规则放一个带标记的分区里，方便以后认出来、也好删：

```
# ===== git-ignore 自动整理 <今天的日期> =====
## B 依赖/缓存目录
...

## A 脚本跑出来的产物
...
```

**追加规则的方法（别破坏旧内容）：**
- 文件**已存在**：用 PowerShell 只**追加**，绝不全量重写（旧文件里可能有用 GBK 写坏的乱码注释，一重写就真坏了）：
  ```powershell
  $block = @'
  规则1
  规则2
  '@
  Add-Content -Path .gitignore -Encoding utf8 -Value $block
  ```
- 文件**不存在**：用 Write 工具新建一个 UTF-8（无 BOM）的文件。
- 加之前跟现有规则**去重**（同一文件已有规则就不加了）。
- 子项目（比如 LangChainRAG）自己有 `.gitignore`、且已覆盖 → 别在根目录重复加。

### 第五步：取消跟踪用户同意的已提交垃圾

确认过清单二里的哪些，就只对哪些执行：

```powershell
git rm --cached "相对路径/文件名"
```

`--cached` 的意思是：**只从 git 的账本里划掉，硬盘上的文件原样保留**。绝不能漏掉 `--cached`——漏了就是真删用户文件。

### 第六步：收尾自查 + 报告

1. 再跑一次第一步的两条命令，确认：
   - 清单一里被忽略的文件，不再出现在"未跟踪"结果里
   - 清单二里取消跟踪的文件，已从"已跟踪"名单消失
2. 确认 `git status` 里剩下的确实没有误伤重要文件。
3. 向用户报告：加了哪几条规则、取消了哪几个文件的跟踪、**接下来建议跑一次 `/git-save` 把这次的改动提交掉**（取消跟踪的记录要在下次提交里才会生效，属正常现象）。

## 注意事项

- **永远先确认再动手。** 用户明确选了"先看清单再动手"，这是硬规矩，不是可选优化。
- **绝不忽略源代码、脚本、文档、配置文件**，这些是用户的成果。
- **绝不 `git rm`（不带 `--cached`）**真删文件；最多 `git rm --cached`。
- **别乱写宽泛规则**：宁可一条一条写具体路径，也别写 `*.csv`、`*.json`、`*.py` 这种一刀切。
- 看到 `.gitignore` 里有乱码注释（中文变 `锟斤拷` 那种），**别去重写修复**（编码已坏，重写更糟），只追加新分区；可提醒用户这是历史遗留问题。
- `.vscode` 这类要不要忽略取决于用户——有的团队想共享调试配置。个人学习仓库一般可忽略，但**仍然交给用户点头**。
- 拿不准就停下来问，别猜。
