# evaluate：三层评估体系

## 这个技能做什么

给 skill / 工作流做三层体检，各回答一个问题：

1. **L1 任务级评估** —— 这一次任务，每一步走对没？（随堂小测）
2. **L2 skill 级评估** —— 同一个 skill 反复用，稳不稳、卡在哪？（单元考：同一份卷子反复考）
3. **L3 系统级评估** —— 整套自动化会不会跑偏、倒退、失控？（期末体检）

核心思路：**能客观量化的交给脚本测，需要判断的才写进报告**，不靠感觉打分。

## 共用约定

### 报告统一存档，留历史

三层报告都存进 `.claude/skills/evaluate/reports/` 下的三个子目录，每份带时间戳：

- `reports/task/` —— L1 阶段小卡
- `reports/skill/<skill名>/` —— L2 每轮测评
- `reports/system/` —— L3 体检

**没有历史就没有"回归/漂移"可言**，所以都留档。`reports/` 已被 .gitignore 忽略，不入库，别手动删。

### 红线（必须遵守，任何一层都适用）

1. **测评只在隔离环境跑**，绝不碰用户真实仓库和真实远程。跑 git-save 这类会推送的 skill，考题里必须用临时目录搭一个本地 bare remote 当假远程，**绝不真推 GitHub**。
2. **绝不 `git push --force`**，绝不删用户数据。
3. 评估只出报告/小卡，**不改被评的代码**。
4. 评估对象由用户指定，**不默认扫全项目**。
5. **不编造测量值**：脚本没跑出来就写"未测量"，不猜、不编。

## L1 任务级评估：阶段小卡（随任务自动，开销小）

**什么时候用**：正在跑某个流程/任务，想每完成一个阶段就确认一下"这步做没做对"，跑偏了当场发现，别让一个小错传到最后的结论里。

**做法**：在每个阶段边界，把本阶段该有的客观结果写成一个 `spec` 小清单（JSON），交给 `measure.py` 去量：

```powershell
python .claude/skills/evaluate/scripts/measure.py spec <spec文件路径>
```

`measure.py` 会逐条跑检查，全过打 PASS，有不过打 FAIL，并把一张"阶段小卡"写进 `reports/task/`。spec 长这样：

```json
{
  "task": "某次任务名",
  "stage": "第一步：拿改动清单",
  "checks": [
    {"kind": "exists", "path": "save-gate"},
    {"kind": "contains", "path": "save-gate/quality.passed", "needle": "PASS"}
  ],
  "note": ""
}
```

支持的可测项见脚本内 `--help`（文件/目录在不在、文件里含不含某内容、工作区干不干净等）。

**试点接入（下一阶段再做，先别铺开）**：挑一个流程型 skill（候选：git-save / comment-check），在它的阶段边界接上小卡。先接一个证明链路通，再逐个推广——**别一次性大改所有 skill**。

## L2 skill 级评估：稳定度测评（手动）

**什么时候用**：想验证某个 skill 稳不稳、或者改完一个 skill 后想确认它没变坏（回归测试）。说法：`测评一下 git-save` / `跑 /evaluate`。

**做法**：

1. 列出 `cases/<skill>/` 下的标准考题，先给用户看一眼考哪些。
2. **逐题执行**：
   - 读考题，按考题里的"运行前准备"搭隔离环境（临时仓库，绝不碰真实远程）；
   - 加载被测 skill 真跑一遍；
   - 对照考题里的**该做到 / 该拦住 / 不应做**三个预期逐条核对——能客观量的用命令或 `measure.py` 核对，需要判断的（如"报告像不像样"）用一两句说明。
3. 汇总成报告 `reports/skill/<skill>/<日期>.md`，固定要点：
   - 通过 x/y 题；
   - 每题 pass/fail + 一句话原因；
   - 最常卡在哪一步、花了多久；
   - 改进建议。
4. 给结论：**稳定** / **有波动**（给出能复现的路径）/ **不稳定**（给最小修复建议）。

**考题怎么攒**：从真实任务里挑有代表性的沉淀进 `cases/`，**不是一次造完**。每攒几条，测评的"回归网"就密一层——这正是按需求迭代优化 skill 的依据。

## L3 系统级评估：体检（手动 /system-check）

**什么时候用**：想确认整套机制没漂移、没回归、没失控。说法：`体检` / `/system-check`。

**做法**：

1. **客观信号**：先跑

   ```powershell
   python .claude/skills/evaluate/scripts/system_check.py
   ```

   它会收集：工作区干不干净、save-gate 标记有没有残留过期、reports 有没有越堆越大、.gitignore 有没有漏。结果按 PASS / WARN / FAIL 打印。
2. **判断项**（脚本测不了的，逐条人工核对）：
   - **漂移**：对照各 skill 的 SKILL.md 原文，最近实际行为有没有悄悄放宽判定标准、改输出格式、跳流程？
   - **回归**：抽查一条关键链路还通不通（比如 git-save 全流程、comment-check 出报告）。
   - **失控**：有没有越权动作痕迹——`push --force`、没被要求却改了别的文件、save-gate 标记残留过期、某步反复重试狂烧 token。
3. 汇总成报告 `reports/system/<日期>.md`，每项标 PASS / WARN / FAIL。**任一 FAIL，建议先拦下相关提交修好再继续**。

## 报告统一格式

```
## <层级名>评估报告（<日期>）

### 结果汇总
- 整体：PASS / WARN / FAIL
- 通过 x/y 项

### 逐项
- 项目名：PASS / WARN / FAIL —— 一句话 + 证据（脚本输出或第几行/哪条命令）

### 结论与建议
（大白话：问题是什么、最该先处理哪个、怎么改）
```

报告要求：每项都给证据；不堆术语；做得好的地方也点一句。

## 注意事项

- 评估本身也花时间花 token，**按需跑**：L1 随任务开销小，L2/L3 想验证或怀疑时才手动跑。
- 脚本测不过时，先怀疑脚本/环境/隔离没搭对，再下"被测 skill 坏了"的结论。
